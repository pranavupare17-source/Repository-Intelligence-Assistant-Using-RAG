    Q1

    "Why did you avoid LangChain, LlamaIndex, or Haystack?"

    Frameworks like LangChain wrap retrieval in monolithic black boxes designed for unstructured prose. They treat code like plain text, splitting arbitrarily on newline or token boundaries, which cuts loops and conditionals in half. By hand-rolling our system in pure Python, we maintain complete control over concrete syntax tree traversal, context enrichment, and vector math.

    Q2

    "How does FAISS IndexFlatIP mathematically compute Cosine Similarity?"

    Cosine similarity is mathematically defined as:

    $$\cos(\theta) = \frac{A \cdot B}{\|A\|_2 \|B\|_2}$$

    In embedder.py, we apply $L_2$ normalization to all vectors so that $\|A\|_2 = 1$ and $\|B\|_2 = 1$. Under this constraint, the denominator equals 1, making Inner Product $A \cdot B \equiv \cos(\theta)$. Using FAISS IndexFlatIP avoids expensive runtime vector division.

    Q3

    "What is the role of the Synthetic Context Header?"

    Code exhibits high lexical repetition (e.g. methods named verify(), initialize(), charge()). In isolation, embedding vectors lack semantic identity. We synthesize a structured header:

    File: auth.py | Class: TokenService | Method: verify_token(...) | Docstring: Validates token...

    This anchors the dense vector in its surrounding software architecture.

    Q4

    "What is the Value of the Phase 3 Dependency Knowledge Graph?"

    Semantic vector search is excellent for conceptual similarity, but blind to deterministic runtime flow. Our Phase 3 Knowledge Graph parses call-sites and imports using tree-sitter into a directed NetworkX graph. This allows our system to answer structural questions like "What happens if I change verify_token?" by traversing upstream callers and computing the transitive blast radius.
